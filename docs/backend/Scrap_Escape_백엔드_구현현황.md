# Scrap Escape — 기획 대비 백엔드 구현 현황

기준일: 2026-10-26. 기존 7일·3개 수리 버전이 아니라 현재 소스의 10일·4개 수리·비밀의 방 확장 버전을 검토했다.

[전체 API 명세서](../api/Scrap_Escape_API_명세서.md) · [OpenAPI3.1 JSON](../api/openapi.json)

## 1. 결론

핵심 게임 로직과 비밀의 방, 변경 요청 재전송 방지는 구현되어 있다. HTTP API는16개이며 실제 MySQL 테스트115개가 실패·오류·건너뜀 없이 통과했다. 서버 재시작 후에도 저장된 응답이 복원되는 것을 실제 HTTP로 확인했다. 프론트엔드·플레이 밸런스 검증은 남아 있다.

사용자 결정: GAP-01 시간 제한 우선 유지, GAP-02 추가 구현 완료, GAP-03 서버 미리보기·화면 연동 계약 구현 완료, GAP-04 결과 보존/순위표 보류, GAP-05 완성 후 플레이로 검토. 기존 판 자동 삭제나 순위표는 이번에 구현하지 않았다.

## 4. 미완성·부분 구현·미검증 항목

### GAP-01. 두 기한을 한 행동에서 모두 넘을 때 실패 사유 — 사용자 확정·현재 동작 유지

최종 확정: 행동 완료 시 두 기한을 모두 넘겼으면 전체 시간 제한(TIME_LIMIT)을 우선한다. 질병 기한만 넘겼으면 UNTREATED_DISEASE다.

현재 `GameRepository.finish`는 행동 완료 시 `elapsed>=240`이면 무조건 TIME_LIMIT를 먼저 선택하고, 그 외일 때 질병 기한을 검사한다. 따라서 질병 기한이 더 먼저 지났어도 한 행동에서 둘 다 넘으면 시간 제한을 원인으로 표시한다. 질병이 없어도 같은 행동에서 생존 기한을 넘겨 실패하므로, 사용자가 이 우선순위를 유지하기로 했다.

실제 재현:

| 조건 | 값 |
|---|---|
| 행동 시작 경과 시간 |232h, 시각00:00 |
| 발병 시점·치료 기한 |162h·234h |
| 전체 생존 기한 |240h |
| 행동 |질병 중 밤 탐색9h |
| 완료 시점 |241h |
| 현재 응답 |FAILED / TIME_LIMIT |
| 먼저 지난 기한 |질병 / 234h. 최종 사유 선택은 TIME_LIMIT 우선 |

[실제 HTTP 재현 응답](../api/examples/GAP-01-deadline-priority.json)

추가 수정 없음. 위 예시는 기존 불일치를 수정해야 한다는 뜻이 아니라 확정한 우선순위의 회귀 검증 자료로 유지한다.

### GAP-02. 일반 행동의 재전송 중복 제거 — 구현·검증 완료

생성을 포함한 변경 API11개에 `Idempotency-Key` UUID 헤더를 추가했다. 같은 번호와 같은 행동은 최초 응답을 재사용하고 시간·체력·재료를 다시 변경하지 않는다. 다른 행동에 같은 번호를 사용하면409다. 헤더가 없거나 번호가 다르면 별도 요청으로 처리된다. 프론트에서는 행동마다 번호를 생성하고 네트워크 재시도에만 재사용해야 한다.

요청 결과를 MySQL `api_request`에 게임 변경과 함께 저장한다. 동시 도착·게임 종료 후·서버 재시작 후 재시도를 검증했다. 오류는 변경과 기록을 함께 취소한다. 재사용 응답은 과거 상태이므로 프론트는 최신 State를 다시 조회한다.

[구현·검증 기록](Scrap_Escape_요청중복방지_구현_검증.md)

### GAP-03. 안전지대 행동 미리보기·화면 연결 — 구현 완료

SE-16 GET /api/games/{id}/screen에서 State·장소 카드와 휴식8개 선택지, 양쪽 재료의 이동/세척/폐기, 수리4개, 치료·탈출 미리보기를 한 번에 제공한다. 가능한 행동은 완료 예상값, 불가능한 행동은 이유/코드와 projected=null을 제공한다. 기한 초과는 경고하며 차단하지 않는다. 세척 대상의 만료 보호·치료 완료 기한·CLEAN 합칠 공간까지 반영한다.

탐색/비밀의 방은 기존 비용·확률 정보를 재사용한다. 확률 결과를 미리 확정하지 않는다. 화면별 필드/버튼 제한 매핑과 JavaScript 공통 요청 모듈도 추가했다. 실제 HUD·선택창 디자인과 브라우저 검증은 다음 단계다.

[화면 연동 명세](../frontend/Scrap_Escape_화면_연동_명세.md) · [구현·검증](Scrap_Escape_화면연동_구현_검증.md)

### GAP-04. 종료·방치 게임 데이터 정리 — 사용자 검토 대기

종료 판과 오래된 판은 DB에 남는다. 게임 전체 삭제 HTTP API, 보존 기간, 자동 정리 배치, 미완료 판 정리 정책은 없다. 최초 기획에서도 ‘이전 판 정리 정책은 구현 환경에서 결정’으로 남긴 항목이다. 재료 묶음을 삭제하는 SE-07은 게임 전체 정리와 다르다.

검토 선택지: (1) 결과 화면 확인 후 판 전체 삭제, (2) 최종 요약만 별도 저장하고 상세 데이터 정리. 후자는 추후 순위표에 재사용할 수 있다. 추천은 성공/실패·소요 시간·수리/탐색/방/열쇠 통계 등 최종 요약 보존이며, 순위 산정·이름 입력·미완료 판 정리 시점은 선택 후 설계한다. 현재는 전체 데이터 보존을 유지한다. 요청 이력도 연결되어 있으므로 삭제 후 재전송 보장 범위까지 함께 정해야 한다.

### GAP-05. 실제 게임 밸런스·진행 길이 — 완성 후 플레이로 조율

로직·경계·DB·HTTP 테스트는 했지만 다수 판의 탈출률·평균 행동 수·실제 플레이 길이는 검증하지 않았다. 재료2종 분배에 따른 세척액 수요,50%·1회분 공급의 충분성, 질병·폭풍·특수 재료 수요, 방을 못 찾아도 탈출 가능한지 등을 플레이/시뮬레이션으로 확인해야 한다.

## 6. 검증 근거

- 기존90개+요청 중복 방지14개+화면 미리보기11개=MySQL 테스트115개, 실패0·오류0·건너뜀0. JAR 빌드 성공.
- 기존15개API 실제 응답20개에 중복 방지 HTTP 예시7개를 추가했다. 정상 재전송·400·409·재시작 후 원래 응답 복원을 확인했다.
- 이전 점검에서 OpenAPI15개작업과 Controller를 대조하고29개 응답 스키마·예시27개의 JSON 구조를 검증했다.
- fresh/legacy 마이그레이션 테스트를 포함한다. 이번 실제 HTTP 검증은 scrap_escape_test와18080포트만 사용했고 생성한 판만 정리했다. 개인 scrap_escape DB 및 Notion 원문은 변경하지 않았다.
- [요청 중복 방지 상세 검증](Scrap_Escape_요청중복방지_구현_검증.md)

## 7. 현재 다음 순서

화면 정보/버튼 제한 매핑, 서버 미리보기, 공통 통신 모듈의 세 가지 준비를 완료했다. 새 GET screen을 포함해 API16개이며, 전체 MySQL115개·JavaScript11개 테스트가 통과했다. 실제 JAR에서 화면 조회·미리보기와 실행 결과 대조·정적 모듈 제공·JavaScript 생성/휴식 연동을 확인했다.

다음은 기존 배치대로 실제 메인 HUD와 안전지대 창부터 구현하는 것이다. 모든 창의 상태 표시·X, 실행 불가 이유 표시, 처리 중 버튼 차단, 수동 재시도 버튼을 연결한다. GAP-04 결과 보존/순위표는 결정 후, GAP-05는 완성 후 플레이로 조율한다. 별도 프론트 프레임워크 도입은 필요 없다.

기능 변경마다 docs의 명세·예시·구현 현황을 함께 갱신한다.
