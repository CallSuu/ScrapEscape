# 요청 중복 방지 구현·검증

기준일:2026-10-26. GAP-02 추가 구현. [API 명세](../api/Scrap_Escape_API_명세서.md) · [구현 현황](Scrap_Escape_백엔드_구현현황.md)

## 구현

생성 포함 변경 API11개에 선택 Idempotency-Key UUID 헤더를 연결했다. 요청 지문과 원래 JSON을 Flyway V6의 api_request에 저장한다. 동일 키의 INSERT/행 잠금으로 동시 재전송을 직렬화하고 게임 변경과 기록을 하나의 트랜잭션으로 커밋한다. 기존 JSON 응답·15개 경로는 유지한다.

같은 행동 재시도는 원래200/201과 JSON, Idempotency-Replayed:true. 다른 행동에 번호 재사용은409 IDEMPOTENCY_KEY_REUSED, 잘못된 UUID는400 INVALID_IDEMPOTENCY_KEY. 헤더 생략·다른 번호는 별도 행동이다. 오류는 기록하지 않으며 게임/기록을 함께 되돌린다.200+FAILED는 저장한다.

## 실행 검증

- Java17, 전용 MySQL scrap_escape_test에서 전체104개: 실패0·오류0·건너뜀0. test --rerun-tasks 및 bootJar 성공.
- 신규14개: 생성·휴식·탐색 재시도, 다른 입력/경로/게임 충돌, 무키/다른키, UUID 형식/대소문자/정규화 DTO, 동시 요청, 이후 행동 후 과거 응답, 도메인 오류 후 재시도, 삭제된 묶음·종료 판 재시도, FAILED 결과, DB 후반 오류 시 행동/기록 롤백.
- 마이그레이션 테스트3개 포함: 새 DB·기존 DB 보존·V4 이후 V5/V6 적용 확인.
- 실제 JAR18080포트에서 새 게임201 재사용, 휴식200 재사용(6시간이 추가로 흐르지 않음), 충돌409·잘못된 번호400 확인.
- 프로세스를 종료하고 같은 테스트 DB로 새 프로세스를 띄운 뒤 동일 휴식 요청의 헤더true·원래JSON 완전 일치를 확인했다.
- [실제 HTTP 예시7개](../api/examples): idempotency-create, create-replay, rest, rest-replay, conflict, invalid, restart.
- 개인 게임 DB scrap_escape는 변경하지 않았다. 테스트 서버를 종료하고 중복 요청 검증에서 생성한 판과 연결된 요청 이력을 정리했다. 일반 HTTP smoke도 통과했으며 병원 흐름용 테스트 판은 전용 DB에 남아 있다.
- 독립 코드 검토에서 조치가 필요한 문제는 발견하지 않았다. 검토와 테스트 통과는 UI/게임 밸런스 검증을 대체하지 않는다.

## 프론트 계약과 남은 정책

행동별 UUID를 생성하고 응답 유실 재시도에는 같은 번호를 사용한다. 버튼 처리 중 비활성화도 적용한다. 재사용 JSON은 그 행동 당시의 상태이므로 최신 State를 GET한 후 화면에 반영한다. 요청 이력은 서버 재시작에도 남으며 게임 삭제 시 함께 삭제된다. TTL·결과 요약 저장·순위표는 GAP-04 결정 후 구현한다. 현재 자동 삭제는 없다.

GAP-01은 사용자 결정에 따라 TIME_LIMIT 우선 유지. GAP-03 통합 미리보기는 프론트 없이도 추가 가능하나 아직 미구현. GAP-05는 완성 후 플레이로 조율한다.
